# RFC 0016: Compile-Time Execution

| | |
|---|---|
| **Status** | Accepted |
| **Authors** | Paco Core Team |
| **Created** | 2026-09-26 |

## Summary

`comptime` is Paco's only metaprogramming mechanism. A `comptime` block or `comptime fn` runs ordinary Paco code during compilation, with access to type information, and can generate code. Generated code is type-checked exactly like hand-written code. `#[derive(...)]` is a `comptime` generator applied to a type. Compile-time execution is sandboxed: no I/O, no FFI, no tasks, no clock, and a bounded number of steps. A value computed at compile time is the same value compiled code computes for the same expression. Paco has no syntax macros. Attributes are written `#[name]` or `#[name(args)]`.

## Motivation

Programs need code that follows from the structure of their types: formatting, serialization, equality, schema-aware accessors. Writing it by hand is repetitive and drifts out of sync with the type.

Runtime reflection or metatables solve this by moving type information and dispatch into the running program. That costs performance and turns type errors into runtime failures.

Syntax macros solve it by transforming tokens before type checking. They require a second language inside the first, with its own hygiene rules and error messages that point into generated code.

`comptime` generates the code at compile time, from typed information, in ordinary Paco, and checks the result with the ordinary type checker.

## Guide-level explanation

A `comptime` expression or block is evaluated during compilation, and its result is used as a constant:

```paco
const TABLE_SIZE: i64 = comptime { 1 << 10 };
```

A `comptime fn` runs only at compile time. It can take a `type` as a parameter, inspect it, and return `Code` that the compiler inserts into the program:

```paco
comptime fn derive_serialization(T: type) -> Code {
    // walk T's fields and generate the serializer
}
```

`#[derive(...)]` applies generators to a type. The generated methods are ordinary methods, checked and compiled like any other:

```paco
#[derive(Display, Serialize)]
struct User {
    name: string,
    age:  i64,
}

fn main() {
    let u = User { name: "Ana", age: 30 };
    print(u.display());
}
```

If a generator produces code that does not type-check, the error is reported like any other type error in the program.

`comptime` code cannot read files, call foreign functions, spawn tasks, or read the clock. It computes exactly what the same code computes at run time, so a constant folded at compile time never differs from the value the program would compute.

There are no syntax macros. Code that needs to embed a domain-specific language, or to capture the source text of an expression, uses a library parser or an external code generator run before `paco build`.

### Attributes

Attributes annotate the item that follows them:

```paco
#[derive(Display, Clone)]
struct Point { x: f64, y: f64 }

#[repr(C)]
struct Header { tag: u32, len: u32 }

#[test]
fn point_display() {
    assert_eq(Point { x: 1.0, y: 2.0 }.display(), "Point { x: 1, y: 2 }");
}

#[allow(unhandled_result)]
fn flush_best_effort(log: &mut Log) {
    log.flush();   // returns a Result, ignored on purpose
}
```

`@` is not an attribute marker. It is used only for binding a name in a pattern:

```paco
match n {
    d @ 1..=9 => print(d),
    _ => {}
}
```

## Reference-level explanation

**Forms.** `comptime` appears in three places:

- `comptime { ... }` or `comptime expr`: an expression evaluated at compile time. Its value becomes a constant in the compiled program.
- `comptime fn`: a function callable only at compile time. `comptime` does not combine with `unsafe` or `extern`.
- `#[derive(Name, ...)]`: runs the generator for each named derive on the annotated type and inserts the resulting items.

**What comptime sees.** Compile-time code operates on typed, resolved constructs only. It can receive types as `type` values, enumerate a struct's fields and their types, get a type's name, and build `Code` values that become items or expressions. It has no access to the token stream or to source text before parsing and name resolution.

**Checking generated code.** Code produced at compile time goes through the same name resolution, type checking, borrow checking and code generation as hand-written code. Nothing generated bypasses verification.

**Sandbox.** Compile-time execution may not:

- perform I/O,
- call foreign functions,
- spawn tasks or use channels,
- read the clock.

Execution is bounded by a step budget. Exceeding it is a compile error.

**Value agreement.** A value computed at compile time is the value compiled code computes for the same expression:

- Integer arithmetic follows the debug-profile overflow rule ([RFC 0006](0006-integer-overflow.md)); an overflow during compile-time evaluation is a compile error.
- Float arithmetic produces the same results, and floats print the same digits ([RFC 0007](0007-floating-point-types.md)).
- Numeric conversions and formatting produce the same results.

Compile-time evaluation behaves the same under `paco run`, `paco build` and `paco build --release`.

**No syntax macros.** There is no `macro` keyword, no `macro_rules!`-style pattern macro, and no procedural macro over token streams. This rules out, in the language:

- embedded DSLs parsed at compile time from custom syntax (SQL, HTML templates, regular expressions compiled to automata),
- assertions that report the literal source text of their arguments.

Adding a syntax-level mechanism requires a new RFC based on concrete cases `comptime` cannot cover.

**Attribute syntax.** An attribute is `#[name]` or `#[name(arg, ...)]`, placed before an item, a struct or enum member, a trait member, or a function in an `extern` block. Arguments are literals, paths, identifiers, or nested attributes. Attributes defined by the language include `#[test]`, `#[derive(...)]`, `#[repr(C)]` and `#[allow(...)]`. `@` appears only in patterns, as `name @ pattern`.

## Drawbacks

The compiler must contain an evaluator for the subset of Paco that `comptime` accepts, and that evaluator must agree with compiled code. Any divergence is a bug that value agreement forbids, and it needs dedicated testing.

Without syntax macros, some patterns have no in-language solution: rich assertion messages showing source text, and embedded DSLs checked at build time. They need a library or an external generator.

The sandbox excludes useful build-time work, such as reading a schema file to generate types. That work has to happen in a separate step before compilation.

## Rationale and alternatives

Runtime reflection or metatables allow the most dynamism, but they move dispatch and type information into the running program, block optimization, and turn type errors into runtime errors.

Declarative syntax macros (`macro_rules!`-style) give pattern matching over token trees. They need a hygiene model, and errors inside expansions are hard to read. They add a second language that users must learn alongside `comptime`.

Procedural macros over token streams require the compiler to expose a stable token or syntax-tree API that library authors depend on permanently.

A single mechanism operating on typed constructs keeps one model to teach, format and diagnose. Declining syntax macros is also reversible: they can be added by a later RFC, whereas a macro system that proves unworkable is hard to remove once code depends on it.

An unrestricted compile-time environment would allow reading files and calling foreign code during the build. The sandbox keeps builds reproducible and keeps compile-time results equal to run-time results.

## Prior art

Zig's `comptime` runs ordinary Zig code at compile time with access to types. C++ `constexpr` evaluates functions at compile time under restrictions and requires results equal to run-time evaluation. Rust's `macro_rules!` and procedural macros are the syntax-macro model, with documented hygiene and diagnostic difficulties. Lisp macros are the general model of syntax-level metaprogramming. Lua metatables and Java reflection are the runtime model.

## Unresolved questions

None.

## Future possibilities

A structured `assert_eq` that reports field-by-field differences using compile-time reflection could close part of the gap left by the absence of source-capturing assertion macros.

A syntax-level mechanism could be proposed in a new RFC if practical cases accumulate that `comptime` cannot cover.
